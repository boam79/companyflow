# PRD v1.3 분석

분석일: 2026-09-16

상태: Planner 초안. 사용자 확인 전.

## 제품 정의

지정 PC의 브라우저(OPFS + SQLite WASM)에 업무 원본을 두고, 중앙(Supabase)은 인증·회사 등록·라이선스·암호화 Relay만 담당하는 **Local-first 모듈형 ERP**.

직원·입퇴사·명찰, 구매, 입출고·재고, 자산, 계약을 연결한다. 새 회사는 코드 수정, 앱 재배포, 수동 DB 구조 변경 없이 설정과 Template만으로 사용을 시작한다.

## 잘 정의된 점

- 구매요청 → 결재 → 발주 → 분할수령·검수 → 창고/자산/비재고 배분. 구매 없는 직접 입고는 별도 경로.
- 상태 라벨로 재고를 증감하지 않는다. `confirm_order`, `post_receipt` 등 내부 명령으로 처리한다.
- 회사 격리: B회사 변경은 B에만 게시. `if company_id == B` 금지.
- AC-01~34가 원자성, 중복 방지, 통계 원본 일치, A/B 회귀를 테스트 문장으로 적는다.
- 평문 업무 원본은 Supabase에 올리지 않는다.

## 이번 개발 / 후속

**포함:** 직원·입퇴사·명찰, 기준정보, 구매, 입출고·재고, 자산, 계약 OCR, 통계·Excel, 회사 설정·Workflow·문서, Relay, 백업.

**후속:** 다중 PC 공동 편집, 회계·급여·세무, 법적 전자서명, 재고 원가, 다중 단위·lot, 진행 업무 Template 이관, 앱 종료 중 외부 알림.

구매 구분과 재고·자산 관리 방식은 다른 값이다. 한 발주서에 일반 비품·자재·서비스를 섞을 수 있다.

## 핵심 리스크

1. SQLite WASM + OPFS VFS + Worker + 단일 쓰기 탭이 1단계 조건인데, VFS·브라우저·호스팅은 미정이다.
2. PRD 11.2 첫날 목록이 단계 1~3을 한 번에 담는다. 실행 단위는 11.1의 **단계 1. 기반**만으로 자른다.
3. 필드·Workflow·문서 편집기를 처음부터 완전 구현하면 구매·재고가 늦어진다. 설정 복사와 버전 식별부터 둔다.
4. Relay 키, 백업 암호, 로컬 DB 암호화가 미정인 채 AC-20~22가 있다. 확정 전에 휴대폰 전송·실백업을 켜지 않는다.
5. 원본이 한 브라우저 프로필이다. 저장소 삭제·PC 고장 = 업무 원본 손실.
6. 같은 브라우저 프로필의 계정 분리는 앱 권한일 뿐, 물리 격리는 OS/프로필 단위다.
7. Tesseract.js 한글 계약 OCR 품질은 검증 전이다. 자동 추출은 샘플 시험 후.
8. 품목 수, 거래량, 첨부 용량, 지원 브라우저, 원장 재계산 한도가 없다.
9. 직원·계약 개인정보가 로컬에 남고 백업 암호는 미정이다.
10. WASM/Worker/OPFS는 호스팅 헤더에 민감하다. 헤더 검증 전에 실데이터 일정을 잡지 않는다.

## 착수 해석 (권장)

PRD 11.1을 실행 순서로 채택한다. 11.2는 백로그 초안이다.

단계 1 완료의 의미: 운영 관리자가 회사를 등록하고, 회사 관리자가 지정 PC에서 OPFS/SQLite를 초기화하며, 재실행 후 데이터가 남고, 두 회사 DB가 섞이지 않고, 쓰기 탭이 하나뿐이다.

다음 실행 단위는 [backlog.md](backlog.md)의 T1~T4다. 구매·재고 화면은 그 이후다.

## 열린 질문 (사용자 확인)

1. 첫 구현 범위를 T1~T4(단계 1 기반)로 자르는가.
2. 배포 호스팅을 언제 정하는가. 기능 검증은 배포 HTTPS URL만 사용한다.
3. 최초 운영 관리자를 Supabase 대시보드에서 수동 지정해도 되는가.
